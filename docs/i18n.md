# Internationalisation

## Locales

23 languages, one JSON file each, in `packages/shared/src/locales/`:

`en` `fr` `de` `es` `it` `pt` `nl` `pl` `cs` `ru` `uk` `tr` `ar` `ja` `ko` `zh` `da` `nb` `sv` `fi` `hu` `ro` `el`

`en.json` is the source of truth: a key exists if and only if it exists in `en.json`.

## Rules

1. **No hardcoded user-facing string.** Labels, placeholders, tooltips, dialog text, button text, error messages and notifications all use `t('section.key')` from `react-i18next`.
2. **Every key in all 23 files.** Adding, renaming or removing a key means editing all 23.
3. **Real translations.** Each file holds the text in its own language — never the English string as a placeholder. Keep product and protocol names (Seedora, Transmission, DHT, PEX, µTP) untranslated.
4. **Preserve interpolation.** `{{variable}}` placeholders must appear, unchanged, in every translation.
5. **Do not select DOM elements by translated text** (placeholder, label). Use a `ref` or a `data-*` attribute.

## Keys

- Dot-separated, namespaced by feature: `toolbar.addTorrent`, `statusBar.freeOfTotal`, `dialog.confirmDelete`.
- Top-level sections in use: `app`, `toolbar`, `statusBar`, `sessionStats`, `filter`, `status`, `torrent`, `priority`, `details`, `peersTab`, `trackersTab`, `optionsTab`, `filesTab`, `contextMenu`, `columnMenu`, `dialog`, `server`, `settings`, `speedTab`, `networkTab`, `downloadTab`, `queueTab`, `prefs`, `notification`. Put a key in the section of the component that owns it; add a section only for a new feature area.
- Keep keys alphabetical inside a section, and in the same order across files.
- Interpolation: `"deleteConfirm": "Delete {{count}} torrents?"` → `t('dialog.deleteConfirm', { count })`.

## Two i18n configs

The locale files are shared, the i18next initialisation is not:

| App | File | How locales are loaded |
|---|---|---|
| Electron | `packages/shared/src/lib/i18n.ts` | `import.meta.glob('../locales/*.json')` — auto-discovers files (Vite only) |
| Web | `apps/web/src/lib/i18n.ts` | 23 static imports and a hand-written `resources` map |

Both detect the language from `navigator.language` and fall back to `en`. `apps/web/tsconfig.json` excludes the shared `lib/i18n.ts` because `import.meta.glob` does not exist in Next.js.

**Adding a language** therefore touches three places:

1. `packages/shared/src/locales/<code>.json` — complete, translated.
2. `apps/web/src/lib/i18n.ts` — the import and the `resources` entry.
3. `packages/shared/src/lib/i18n-utils.ts` — the native name in `LANGUAGE_NAMES` (drives the language picker).

## Gate

```bash
npm run i18n:check
```

(`scripts/i18n-check.mjs`) compares every locale against `en.json` and fails on missing or extra keys. Run it after any locale edit; it is meant to run in CI.

## Current state

- `en` and `fr` have 356 keys. **The other 21 locales have 307: 49 keys are missing** from each (for example `app.close`, `statusBar.freeOfTotal`). i18next falls back to English for these. `i18n:check` fails until they are translated.
- Some values in non-English files are still identical to the English text and need review.
- **Main-process strings are not translated**: the native menu (`src/main/menu.ts`) and the tray menu (`src/main/tray.ts`) are hardcoded English. There is no i18n in the main process yet.
- Remaining hardcoded strings in shared code include units and relative dates in `lib/format.ts`, a few error and status strings in components, and server-side error messages in `apps/web/src/lib/server-actions/`.

All of the above is tracked in the backlog.
